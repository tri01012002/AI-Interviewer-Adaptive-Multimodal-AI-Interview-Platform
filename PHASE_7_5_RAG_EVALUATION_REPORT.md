# Phase 7.5 RAG Evaluation Report

**Date:** 2026-09-02  
**Status:** PARTIAL

## 1. Scope

This phase objectively evaluates and hardens the Phase 7 local retrieval implementation. It does
not add voice, Redis, Celery, browser automation, Kubernetes, external LLMs, persistent vector
storage, or a learned embedding/reranker provider.

## 2. What Was Audited

The live `rag/service.py`, Phase 7 report/audit, interview service integration, retrieval tests,
and dependency declarations were inspected. BM25 is a real `rank_bm25` implementation. Dense
retrieval uses a deterministic hash-vector provider. Fusion uses reciprocal-rank fusion. The
reranker is deterministic term coverage. The corpus is a small in-memory synthetic fixture; there
is no ingestion pipeline or vector database.

Full component classification is recorded in [PHASE_7_5_AUDIT.md](PHASE_7_5_AUDIT.md).

## 3. Implemented

- Synthetic golden dataset, explicitly labeled a local fixture
- Independent Recall@K, Precision@K, MRR, and NDCG@K functions
- Benchmark runner comparing BM25, dense, hybrid, and hybrid plus reranker
- Gap-aware query construction
- Bounded context by chunk count and character count
- Source/document/chunk attribution in formatted context
- Explicit untrusted-context marker for retrieved text
- Empty query and zero-result handling
- Reranker failure fallback to fused candidates
- Retrieval telemetry with strategy, counts, latency, fallback, and versions
- Tests for metric edge cases and retrieval/question-generation influence

## 4. Golden Dataset

`rag/dataset.py` contains four realistic interview-domain cases covering Python async/process
concurrency, Redis invalidation, PostgreSQL isolation, and production model monitoring. It uses
five synthetic attributed chunks and is versioned as `golden-v1`.

This dataset is a **synthetic evaluation fixture** and does not represent production retrieval
quality.

## 6. Reranker Comparison

On this fixture, reranking does **not** improve Recall@K, MRR, or NDCG. Hybrid and hybrid plus
reranker are tied on every reported quality metric. Therefore the reranker has no demonstrated
quality value on this dataset. Measured mean local latency was approximately 0.172 ms for hybrid
and 0.157 ms for hybrid plus reranker; this difference is too small and noisy to justify a
production performance claim. Candidate counts and selections are preserved in the JSON output.

A larger representative dataset is required before deciding whether a learned reranker justifies
its latency/cost.

## 8. RAG to Question Generation

`RAGQuestionService.generate_follow_up_question()` builds a query from position, competency,
and identified gaps, retrieves bounded context, and selects the attributed retrieved question.
Tests prove that Python async/concurrency gaps and Python multiprocessing/isolation gaps produce
different context and different question outputs. Candidate answer text is not used blindly as
the retrieval query.

## 9. Context Budget and Attribution

The service defaults to at most three chunks and 1,200 characters. Formatted context includes
`document_id` and `chunk_id` in an `[UNTRUSTED_CONTEXT ...]` marker. Tests verify the limit and
source attribution. Retrieved text remains data; the retrieval layer does not grant it instruction
priority.

## 10. Isolation and Security

Metadata filters are applied before dense and BM25 retrieval. Competency, role, source type,
version, and language filters are supported. Current documents do not contain tenant IDs because
the current product schema has no retrieval tenant model. Tenant isolation is therefore
**DEFERRED**, not claimed. The prompt-injection fixture is preserved as untrusted content and is
never executed as a command.

## 11. Failure Handling and Observability

Empty queries return an explicit empty result. Zero-score BM25 queries return no lexical
candidates. Reranker exceptions fall back to fused candidates and report `reranker_failed`.
The compatibility question service catches retrieval failures and returns an empty guidance list
or a safe fallback question, allowing the interview path to continue. Telemetry excludes raw
candidate answers and records strategy, candidate/selected counts, latency, fallback reason, and
retrieval/embedding/reranker versions.

## 12. Versioning and Persistence Decision

Current versions are `hybrid-v1`, `deterministic-v1`, `term-coverage-v1`, and `golden-v1`.
Persistent vector storage is **DEFERRED** until document ingestion and corpus lifecycle management
exist. No fake pgvector table or migration was added.

## 14. Production Readiness Assessment

**PARTIAL.** The local hybrid pipeline is behaviorally testable and objectively evaluated on a
synthetic fixture. It is not production-ready: the corpus is in memory, dense embeddings and
reranking are deterministic development implementations, ingestion is absent, no persistent
vector index exists, tenant metadata is not modeled, and the benchmark is too small for quality or
capacity claims.

## 15. Deferred and Not Implemented

- Production embedding provider
- Learned cross-encoder reranker
- Document parser/chunker/metadata enrichment pipeline
- Persistent vector store/pgvector runtime
- Representative production golden dataset
- Retrieval quality regression gates at scale
- Tenant-scoped corpus model
- External LLM integration
- Voice, browser automation, Redis, Celery, Kubernetes
- PostgreSQL verification
